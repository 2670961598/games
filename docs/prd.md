## 1. 产品定位与边界

**一句话定位**：4399 × 抖音——纯手机端竖屏小游戏网站，无限上滑刷小游戏，刷到即玩，玩完即走。

要点：

- 目标形态：移动端浏览器优先（桌面浏览器可用，非优化重点）；无 App、无安装。
- 核心体验闭环：打开 → 上滑刷游戏 → 点进即玩 → 滑走换下一个 → 「我的」里找回玩过的。
- **做**：刷游戏 feed、我的页（历史/时长）、玩家上传游戏、游戏大全（目录全集）。
- **不做（边界清单）**：关注/粉丝等关系链、点赞、评论、弹幕、消息、拍摄/录屏、搜索（首版不做，只做大全目录浏览）、账号体系（访客匿名制，见 §6）、支付。
- 目标用户：碎片时间摸鱼玩家；上传者为轻量 Web 游戏开发者/爱好者。
- 完整稿补：用户画像、竞品参照（4399 目录制 vs 抖音 feed 制各自取什么舍什么）、成功指标定义。

## 2. 竖屏 feed 交互规范

采纳 GAMES-8 结论：**方案 B = CSS scroll-snap（y mandatory）+ 保留式 DOM + LRU iframe 池 + 激活层模式**。

要点：

- **一屏一游戏**：每屏 `100dvh`，`scroll-snap-align: start` + `scroll-snap-stop: always`（一次滑一屏），容器 `overscroll-behavior-y: contain` 防穿透。
- **游戏容器加载时机**：IntersectionObserver（rootMargin ±150%）进入预载区才创建 iframe；已创建的 iframe 永不 detach、永不重设 src（保游戏状态）。
- **预取策略**：当前屏 ±1 屏预载（与预载区取交集）；滚出视口的 section 用 `content-visibility: hidden` 停渲染省资源。
- **LRU iframe 池**：上限 N（初值 6，按真实内存画像调整），超限销毁「最久未见」的 iframe——只有滑出 N 屏再远回才重载，可接受。
- **激活层模式**：feed 态给 iframe 盖透明层接管滑动手势；用户点「进入游戏」撤层放行交互；显式退出把手（顶部返回条）回 feed 态。配套接入规范：游戏页自身不可滚。
- **暂停协议**：滚出视口经 postMessage 通知游戏 pause（主循环/音频），回视口 resume。
- feed 内容顺序由**洗牌袋**决定（§3）。
- 完整稿补：feed 态/激活态/加载态/失败态的状态-交互矩阵、真机（iOS Safari）回归清单。

## 3. 洗牌袋规则（精确定义）

每个访客一个「袋子」，feed 的游戏顺序 = 从袋中抽取，保证一轮内不重复、全量覆盖。

要点：

- **袋子构成**：每访客一袋，装入全部**已上架**游戏 ID（上架 = 过审并进入游戏大全，含官方与玩家上传）。
- **抽取规则**：随机**不放回**抽取，抽一个播一个；抽出的顺序即 feed 顺序。
- **袋空语义**：袋空后 feed 提示「已刷完全部 N 款」，此时才允许**重新装满**开始下一轮（新一轮重新随机全量）。
- **新游戏上架**：若当前袋未空——决策项 §11-D2（默认案：直接投入当前袋尾部参与后续抽取，保证新内容及时可见）。
- **下架/驳回**：抽取时校验上架状态，已下架的 ID 抽到即静默跳过并从袋移除。
- **换设备/清缓存语义**：袋子归属访客标识（§6）；标识存 localStorage 时清缓存 = 新访客新袋子（进度丢弃，可接受，匿名轻量产品不做跨端同步——决策项 §11-D1 确认）；换设备同理由。
- 完整稿补：抽取/装袋/入袋伪代码、字段定义（与 §6 shuffle_bags 表对应）、边界用例表（袋空时上架、连续上架、抽到下架品等）。

## 4. 我的页

要点：

- **玩过的游戏**：去重列表，按最近游玩时间倒序；条目 = 封面 + 名称 + 累计时长。
- **每款游戏累计时长**：按 play_sessions 聚合（§6）。
- **总时长**：全部游戏累计之和，页面顶部展示。
- **历史点击再次进入**：点击条目直进该游戏全屏（不走 feed 洗牌顺序——决策项 §11-D3 确认默认案）。
- 上传入口也放在我的页（§5）。
- 完整稿补：页面线框（列表/空态/条目态）、时长统计口径（激活态才计时，feed 态挂机不计——与 §2 暂停协议挂钩）。

## 5. 玩家上传游戏流程

要点：

- **入口**：我的页 →「上传我的游戏」。
- **格式约定**：自包含 HTML 单文件，或 zip（解压后必须含 `index.html` + `game.json`，资源相对路径引用，禁止外链/外网请求，大小上限与完整校验清单见完整稿）。
- **自动校验项**（机器可判，逐条给验收公式）：入口文件存在、game.json 符合 schema（§7）、无外部网络引用、无危险 API（alert/prompt/顶层跳转等）、体积上限、iframe 内可正常加载。
- **审核状态机**：`待审 → 上架 | 驳回`（驳回必附原因）；上架前不可见于大全与 feed。是否保留人工审核环节 = 决策项 §11-D4。
- **上架后**：落入 `games/<type>/<slug>/` 目录约定，纳入游戏大全，进入洗牌袋（按 §3 新游戏入袋规则）。
- 完整稿补：状态机图（含作者侧可见状态）、驳回原因枚举、上传记录与游戏记录的关联（§6 uploads 表）。

## 6. 数据模型

表清单与存储划分（字段级定义在完整稿给出：列名/类型/约束/索引）：

| 表 | 内容 | 存储 |
|---|---|---|
| games | 游戏元数据（对应 game.json）+ 上架状态 | 服务端 |
| levels（关卡配置） | 每游戏关卡参数与数值档位（§8） | 服务端（随游戏分发静态化） |
| visitors（访客标识） | 匿名访客 ID（UUID，localStorage 生成、首次上报注册） | 服务端记录 + localStorage 保存 |
| play_sessions（时长与历史） | 每次游玩会话：游戏、开始/结束、时长 | 服务端（客户端批量上报） |
| shuffle_bags（洗牌袋） | 访客当前袋内容与剩余序列 | localStorage 优先（决策项 §11-D1） |
| uploads（上传记录） | 上传包、校验结果、审核状态 | 服务端 |

要点：

- **存 localStorage**：访客标识、洗牌袋、未上报的游玩记录（离线兜底，恢复网络后合并）。
- **存服务端**：games/levels/uploads 全量；play_sessions 聚合结果（我的页跨设备可恢复时长的口径 = 决策项 §11-D1 附带裁定）。
- 完整稿补：每表字段级定义、localStorage 键名与结构、上报接口的批量/幂等约定。

## 7. 游戏目录结构约定

要点：

- 目录：`games/<type>/<slug>/index.html` + 同目录 `game.json`，全部资源自包含于该目录内。
- `game.json` 元数据字段（大纲级）：`name`（名称）、`type`（类型枚举）、`levelCount`（关卡数）、`difficultyTiers`（数值档位）、`version`；完整稿补全字段 + JSON Schema。
- `<type>` 枚举与里程碑 M4 的「每类型 ≥5 款」对齐（枚举清单在完整稿随批量生产计划定稿）。
- slug 命名规则：小写字母/数字/连字符，全局唯一。

## 8. 关卡与数值差异的表达规范

要点：

- 每款游戏的关卡设计与数值差异**全部用 game.json / levels JSON 参数表达**，代码只实现机制、不写死数值——这是 M4 批量生产（100+）的前提。
- levels 为数组，每关一组参数：难度系数、目标条件、时限、生成种子等（具体键名因游戏类型而异，完整稿给 2–3 个示例游戏的完整参数示例）。
- 数值档位（difficultyTiers）：同一机制下的数值曲线模板（如初/中/高三档），供批量生产时套用变体。
- 完整稿补：参数命名通则（跨游戏类型的一致键名）、校验公式（程序单可断言「改参数即改难度」）。

## 9. 高并发策略的产品侧要求

要点：

- **静态化**：游戏本体（games/ 目录）、游戏大全列表页全静态，可整体上 CDN；feed 页为静态壳 + 数据接口。
- **缓存**：游戏资源长缓存（内容寻址/版本号 URL）；列表/元数据接口短缓存；上传审核态不缓存。
- **接口分页**：大全列表、我的页历史记录必须分页（游标式，按时间倒序）；feed 序列由洗牌袋在客户端生成，不占分页接口。
- **写少读多**：匿名访客制天然无写热点；时长上报客户端聚合批量提交（会话结束/定期 flush），接口幂等。
- 完整稿补：各接口的缓存 TTL 与分页参数约定表。
